## Dev notes

- Reset the database with seed data: `php artisan migrate:fresh --seed` (needs `ADMIN_EMAIL` and `ADMIN_PASSWORD` in `.env`, saved, plus `php artisan optimize:clear` first). Re-seed only the Admin: `php artisan db:seed`.
- Front end: after dropping files that change views or CSS, run `npm run build` (or keep `npm run dev` running in its own terminal tab). `public/build` is not in git. In tests Vite is switched off (`tests/TestCase.php`), so tests do not need a build.
- Run locally: XAMPP only needs **MySQL** running. `cd C:\dev\zks-rms`, `php artisan serve`, open http://127.0.0.1:8000. Terminal is PowerShell in VS Code (keep the server in its own terminal tab).
- `.env` is gitignored and is excluded from the upload zip. Never paste it (it holds `APP_KEY`). Never run `php artisan key:generate` again once real accounts exist (it logs everyone out).
- After dropping files: `php artisan optimize:clear` (MySQL must be running, it clears the `cache` table). Do not run `route:cache` or `config:cache` locally. If tests suddenly say a route is not defined, it is a stale `bootstrap/cache/*.php`: run `optimize:clear` (the zip script already leaves those files out).
- Payment proofs must be **Admin-only** (design doc NFR, Security). Store them on a private disk and serve them through an Admin-only route, not through `storage:link` / the public disk.
- The 24-hour hold needs a scheduled job (every minute is fine). The "hold expires in 2 hours" nudge can run from the same scheduler. Locally that means a second terminal with `php artisan schedule:work`. Built: `reservations:expire-holds` (4a) and `reservations:send-hold-reminders` (6c), both every minute; online they need a real cron (`* * * * * php artisan schedule:run`).
- **Date columns:** tests run on SQLite, where Laravel stores a `date`-cast value as `2026-11-15 00:00:00`; MySQL stores plain dates. Always query date columns (`blocking_date`, `reservation_date`) with `whereDate(...)`, never `where(col, 'Y-m-d')` or `whereBetween` on date strings, or tests will miss rows (this caused the only Chunk 3 test failure).
- Proof images are viewed only through `/admin/proofs/{proof}` (Admin middleware, private disk). Never link them from a public path.
- Upload helper (optional): `tools\make-zk-zip.bat` makes `zk-clean.zip` in Downloads. It leaves out `vendor` (root only), `node_modules`, `.git`, every `.env` file except `.env.example`, logs, SQLite files, uploaded payment proofs, the framework cache, `public\build`, `public\images`, the two lock files and `auth.json`; it checks that no `.env` is in the copy before zipping; it never changes the project folder. ## Locked decisions (summary of `ZKs_RMS_System_Context.md` v2; if this and that file differ, that file wins)

- **Roles:** Guest and Admin only. Admin is one shared resort login. A logged-out visitor sees only Home, Availability, Login and the AI chat. A guest must log in before submitting a reservation. Login replaces any reference-code lookup.
- **Booking Type** (radio, one only): Pool (no cap), Transient (7 pax), Room = Living Area/Sala + Private CR (12 pax), Venue Hall (cap TBD). **Duration:** Whole Day or Half Day, no fixed time blocks; Half Day still blocks the date. Form fields: date, duration, Booking Type, pax, occasion, then proof upload.
- **One group per date, whole resort.** A reserved date blocks every Booking Type.
- **Status badges (use these exact words everywhere): Slot Held, Verifying Payment, Confirmed, Action Needed, Expired, Cancelled.** Never "Pending", "Approved", "Rejected", "Slot Held – Awaiting Downpayment" or "Action Needed – Resubmit".
- **Flow:** submit on an available date → Slot Held (24 hours) → guest uploads GCash proof → Verifying Payment → Admin confirms → Confirmed. Admin flags bad proof → Action Needed → guest re-uploads (hold stays) → Verifying Payment. No proof in 24 hours → Expired and the date reopens by itself. Cancellation processed → Cancelled and the date is released.
- **Walk-ins:** Admin uses the same form and calendar and the reservation is Confirmed immediately (no hold).
- **Reschedule / cancel:** guest requests it from My Reservations, Admin processes it. Allowed only at least 3–5 days before the reserved date; inside the window the request is blocked, and a cancellation forfeits the downpayment. A reschedule needs the new date to be free; the old date is released when Admin approves.
- **Payment proof** is an image plus a status only. No payment amounts are stored.
- **Notifications:** in-app only (no SMS, email, push). Guest bell: status changes, newest first, plus a "hold expires in 2 hours" nudge, empty text "No notifications yet." Admin bell: unread count; proof uploaded, hold near expiry, hold expired, confirmed, cancellation or reschedule requested; a click opens that reservation.
- **Profile** (guest and Admin): name, contact number, email, Edit, Logout. No reservation history or payment info on it.
- **User List (Admin):** guest accounts with name, contact, email, Active/Deactivated, a link to their reservations, search by name, deactivate and reactivate only (a deactivated guest cannot log in or submit; records stay). No delete, no password reset, no editing guests, no creating guests.
- **Activity Log (Admin, read-only):** reservation events (submitted, proof uploaded, confirmed, flagged, expired, cancelled/rescheduled, walk-in entered) and account events (registered, login/logout, profile edited, deactivated/reactivated); each row has date/time, event, who it concerns and actor **Guest / Admin / System**; filters by date, event type, reservation or guest. Not logged: failed logins, page views, clicks.
- **AI Chat (FAQ only):** answers packages, pax caps, whole-resort rule, how to book, GCash steps, the 24-hour hold, reschedule/cancel policy. Cannot book, change, cancel, read guest data or take payment; if it cannot answer it shows the resort's contact details. Chat button on every page. If it cannot be tied to a client-named problem, cut it to a static FAQ page.
- **Reports:** bookings per month and occupancy only (counts).
- **NOT building:** Staff/Manager roles, online payment gateway, SMS/email/push, password reset or email verification, deleting users or editing guest info, editable logs, AI that books or reads guest data, per-room or partial booking, revenue analytics, resubmission limits, reason codes, expiry queues, accounting.
- **Known wrong numbers in the old docs:** docx FR06 (Transient 17, Room 115), the Level 2 text (Room 15) and wireframe Screen 8 / availability and walk-in wireframes (Room 15) are wrong. Use Transient 7 and Room 12.

### Build decisions (Nov 5, approved by the developer; not in the System Context)

1. **No reference codes in the UI.** A guest finds bookings via login; Admin via date, name, status. Reservations keep an internal ID for links only.
2. **Walk-ins have no account.** `reservations.user_id` is nullable, with `guest_name` and `guest_contact` used for walk-ins. Walk-ins do not appear in the User List; they appear in the dashboard and the Activity Log (walk-in entered, actor Admin).
3. **Reschedule/cancel requests are a flag, not a badge.** Field `change_request` (none / reschedule / cancel) plus the requested new date. The reservation stays Confirmed while a request is pending and the date stays blocked until Admin approves. Admin sees a "Reschedule requested" / "Cancellation requested" marker beside the badge.
4. **Notice window = 5 days, kept in a single config value** (`config/zk.php`). Developer approved 5 for now; Jhea may still change it to 3. "Reschedule only once" is NOT enforced.
5. **Auth = hand-written Blade + Tailwind** (changed from Breeze on Nov 5 because Packagist was blocked in the AI sandbox; same result, leaner). One shared login page for guests and Admin; register is guest-only; no password reset, no email verification, no password change screen, no remember me. Login/logout/registered are logged via Laravel's Login/Logout/Registered events. Admin account is seeded.
6. **Pax caps live in one config list;** Venue Hall = no limit until the client gives a number.
7. **Double-booking guard:** a nullable `blocking_date` column with a UNIQUE index (MySQL has no partial unique index). It is set while a reservation is Slot Held, Verifying Payment, Confirmed or Action Needed, and cleared on Expired or Cancelled.

8. **Chunk 3 rules (approved Nov 5).** (a) One booking per date, whole resort; Duration (Whole Day / Half Day) and Booking Type already cover day vs overnight, so there is no extra "stay type" field. (b) A Slot Held reservation blocks its date for 24 hours (`config/zk.php` `hold_hours`); no proof in time means Expired and the date reopens (scheduler, Chunk 4). (c) A guest may cancel their OWN reservation directly **only while it is Slot Held** (no money involved, date frees at once, logged with actor Guest). From Verifying Payment onward cancel/reschedule follows the System Context: guest requests, Admin processes, notice window applies. This Slot Held self-cancel is an addition to the System Context; the button is built in Chunk 5 with My Reservations. Reservation lists live on My Reservations, NOT on the Profile page.

9. **Chunk 3 calendar rules (approved Nov 5).** (a) Earliest bookable date online = tomorrow, kept in `config/zk.php` as `min_advance_days` (1; set 0 for same-day). Same-day bookings are the Admin's walk-ins. This is separate from the 5-day notice window for reschedule/cancel. Mention to Jhea next to the notice-window question. (b) The public calendar shows only "Available" and "Reserved" with the note that a reserved date may reopen; the six badges are shown only to the booking's owner and the Admin.

10. **Chunk 4 rules (approved Nov 5).** (a) **Action Needed never auto-expires**: the guest already paid and the Admin flagged the proof, so the date stays blocked until the guest re-uploads or the Admin cancels (Chunk 5). Only Slot Held expires. (b) **Flagging has no note or reason code**; the guest sees one fixed message asking for a clearer screenshot. (c) Proof files: JPG/PNG/WebP, 5 MB, one image per upload, private disk, Admin-only access (the Admin-only viewing route is built in 4b). (d) Chunk 4 is split: 4a guest upload + expiry, 4b Admin dashboard (reservation list, filter by status, search by guest name, a Verifying Payment count first), `/admin/reservations/{id}` with the proof image, Confirm payment (Confirmed, proof accepted, `confirmed` logged, actor Admin) and Flag proof (Action Needed, proof flagged, `flagged` logged).

11. **Chunk 5 rules (approved Nov 5, built and verified Nov 6, no schema change).** Split: **5a** My Reservations page + nav link + Slot Held self-cancel (decision 8c); **5b** guest reschedule/cancel requests + Admin approve/decline; **5c** Admin walk-in form. Rules: (1) A guest may request a **cancel** while Verifying Payment, Action Needed or Confirmed; a **reschedule** only while Confirmed; only one pending request at a time. (2) Inside the notice window (`config('zk.notice_days')`, 5) the request is blocked and the guest is told to contact the resort. (3) Admin may cancel any reservation at any time, including inside the window, and may tick `downpayment_forfeited` (this and rule 7 are AI additions the developer accepted). (4) Approving a cancel: Cancelled, `blocking_date` cleared, date released. (5) Approving a reschedule: the new date must be free and on/after the earliest bookable date; the date moves and the old one is released; if the new date was taken meanwhile the Admin sees an error and can decline. (6) A pending reschedule does NOT block the requested new date. (7) Declining clears the request; the reservation stays as it was. (8) Every action is logged (actor Guest or Admin; request, approved, declined, cancelled, rescheduled). (9) Walk-in form (Admin): name, contact, date, duration, booking type, pax (same caps), occasion; today or later is allowed; the reservation is created Confirmed at once with no hold and no proof, `is_walk_in` true, logged `walk_in_entered` (actor Admin); it reuses `ReservationService`.

Guest notifications: Confirmed, Action Needed, Expired, cancelled by Admin, request approved/declined, rescheduled, and the "hold expires in 2 hours" nudge; NOT for the guest's own actions. ### Chunk 1 schema (BUILT Nov 5; approach: string columns + PHP backed enums, not MySQL ENUMs)

- **users** (extend the default table): `phone`, `role` (guest/admin, default guest), `is_active` (default true). Email stays the login. `email_verified_at` stays unused.
- **reservations:** `user_id` nullable FK; `guest_name`, `guest_contact` (walk-ins only); `is_walk_in`; `reservation_date`; `duration` (whole_day/half_day); `booking_type` (pool/transient/room/venue_hall); `pax`; `occasion`; `status` (slot_held, verifying_payment, confirmed, action_needed, expired, cancelled); `hold_expires_at`; `hold_reminder_sent_at` (so the 2-hour nudge is sent once); `blocking_date` nullable UNIQUE (decision 7); `change_request` (reschedule/cancel, nullable), `requested_date`, `change_requested_at`; `downpayment_forfeited` (default false, set when a cancellation is marked non-refundable per FR18). Indexes on status, reservation_date, hold_expires_at.
- **payment_proofs:** `reservation_id` FK, `path` (private disk), `status` (for_review/accepted/flagged), `reviewed_at`, timestamps. A re-upload adds a new row; the newest is current. No amounts.
- **user_notifications** (custom, not Laravel's notifications table, to avoid clashing with the Notifiable trait): `user_id`, `reservation_id` nullable, `type`, `message`, `read_at`, `created_at`. Admin bell = rows for the admin user.
- **activity_logs** (insert-only, no updated_at): `category` (reservation/account), `event`, `actor_type` (guest/admin/system), `actor_id` nullable, `user_id` nullable (the guest concerned), `reservation_id` nullable, `description`, `created_at`.
